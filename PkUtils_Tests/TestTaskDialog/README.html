1. Project purpose

TestTaskDialog is a Windows Forms test harness for the shared PK.PkUtils.UI.Dialogs.TaskDialogs.TaskDialogWrapper library. The inspected TestForm exercises ordinary information/question dialogs, a Yes/No/Cancel question, and automatic-close notification and confirmation dialogs. It additionally hosts an experimental feature: displaying three aligned columns of Setting / Ribbon / Project values in the native TaskDialog expander.

The new experiment addresses a practical UI problem: native Windows TaskDialog expanded information is plain text rendered with a proportional font. Padding with a fixed number of characters does not reliably align columns; attempting to replace its font through native control manipulation was not successful in earlier experiments. The current approach instead measures text widths and inserts ordinary spaces until subsequent columns approximately align in pixel coordinates.

Non-goals: replacing the TaskDialog implementation; introducing custom Win32 hooks; changing the production TaskDialogWrapper API; or claiming pixel-perfect table layout in the native DirectUI renderer.

2. Runtime architecture and data flow

TestForm (WinForms UI and event handlers) │ owns dataset/spacing/width/truncation controls ▼ MeasuredSpacesExperiment (test coordinator) │ GetMeasuredRows(dataset) │ _owner.CreateGraphics() + SystemFonts.MessageBoxFont ▼ MeasuredSpaceTableFormatter.Format(...) │ measures text and selects truncation (if needed) │ produces FormatResult { Text, Diagnostics, FullValues } ▼ MeasuredSpacesExperiment ├─ preview → txtMeasuredOutput ├─ diagnostics → txtMeasuredDiagnostics ├─ clipboard → formatted + full original data + diagnostics └─ ShowDialog() → TaskDialogWrapper.QuestionYesNoCancel(...) │ moreDetails = FormatResult.Text ▼ native Windows TaskDialog expander

The TestForm is deliberately thin. All experiment-specific input selection, formatting orchestration and diagnostics are located in an ordinary class named MeasuredSpacesExperiment. The formatter is a separate static algorithmic utility, independent of the test controls. This avoids the earlier confusing TestForm.MeasuredSpaces.cs partial-Form file.

The test uses the existing QuestionYesNoCancel overload and passes generated text via moreDetails. It does not modify the implementation of TaskDialogWrapper.

4. How to use the test application

  1. Build the appropriate TestTaskDialog configuration in Visual Studio and launch the form on Windows.
  2. Select a dataset: ordinary ACM values, very different proportional character widths, long paths/Unicode, or long values sharing a prefix.
  3. Adjust the gap between columns (pixels), approximate maximum table width (pixels), and truncation policy.
  4. Inspect the generated preview and the diagnostic text. Note that a preview control's font can differ from the native TaskDialog's font.
  5. Open the TaskDialog and expand its details to evaluate actual column alignment and unwanted wrapping.
  6. Use the clipboard action to capture formatted text, original untruncated values, and diagnostics for bug reports or comparisons.

The existing non-experiment controls continue to demonstrate the information and question APIs, Yes/No/Cancel result mapping, and two automatic-close behaviors. The measured-space experiment does not replace those tests.

5. MeasuredSpaceTableFormatter — detailed design

5.1 Input and output contract

FormatResult Format(
    Graphics graphics,
    Font font,
    IReadOnlyList<(string Setting, string Ribbon, string Project)> rows,
    string settingHeader,
    string ribbonHeader,
    string projectHeader,
    int columnGapPixels = 20,
    int maxTableWidthPixels = 420,
    MeasuredTextTruncationMode truncationMode = MeasuredTextTruncationMode.Smart)

graphics supplies measurement/DPI context; font is an approximation of the native TaskDialog font; rows are the comparison values; the three headers become the first row. columnGapPixels is the desired gap between columns; maxTableWidthPixels is an estimated usable text area, not the outer dialog's width.

The implementation validates non-null graphics/font/rows, rejects negative gaps, and requires a positive table-width limit. Null individual strings are normalized to empty strings.

The result separates three concerns: Text is what the TaskDialog displays, Diagnostics explains the formatter's decisions, and FullValues retains every original comparison value even when display text was shortened.

5.2 Phase A — measure the original, unmodified table

For each column, determine the maximum measured width across the header and all rows:

settingWidth = max(measured width of each Setting cell)
ribbonWidth  = max(measured width of each Ribbon cell)
projectWidth = max(measured width of each Project cell)

originalWidth = settingWidth + ribbonWidth + projectWidth
                + 2 * columnGapPixels

Measurements call TextRenderer.MeasureText with NoPadding | NoPrefix | SingleLine. The algorithm measures the actual strings, not just character counts.

Critical invariant: if originalWidth <= maxTableWidthPixels, formatting does not truncate any cell — even when the selected policy is Smart or TruncateEnd. It still constructs the aligned text and diagnostic report.

5.3 Phase B — detect overflow and allocate budgets

Only when the original table exceeds the configured width and truncation is enabled does the formatter attempt to shorten it. It preserves setting labels and column headers when feasible, and allocates the remaining space to Ribbon and Project values.

safetyPixels = 12
available = maxTableWidthPixels - settingWidth
            - 2 * columnGapPixels - safetyPixels

minRibbon  = measured width of "Ribbon" header
minProject = measured width of "Project" header

If available < minRibbon + minProject, the algorithm reports that the configured width is too small to preserve labels and headers. It does not promise to fit a table under impossible constraints.

Otherwise, it starts with the minimum header widths and allocates remaining pixels, one unit at a time, until the source columns reach their original widths or the budget is exhausted. The intention is to keep relatively short columns intact and distribute reductions where necessary.

Importantly, only Ribbon and Project value cells (not headers or setting-name cells) are passed to the truncation routine.

5.4 Phase C — truncate a value without breaking Unicode elements

TruncateToWidth first returns the original value if it fits. If not, it inserts the ellipsis character … and uses binary search to find the maximum number of text elements that fit the allocated pixel width. It preserves either a prefix (text…) or a suffix (…text) according to the mode.

Elements uses StringInfo.GetTextElementEnumerator, avoiding arbitrary UTF-16 character splitting. This better handles surrogate pairs and combining characters than a naïve substring; it is still worth testing complex grapheme clusters against the application's target runtime.

Because the output is recomputed against the actual font measurement, the number of retained characters can differ between strings of equal character length.

5.5 Phase D — build the visually aligned text

After truncation, the formatter recalculates the final maximum width of every column. It computes the desired start position of Ribbon and Project:

targetRibbon  = finalSettingWidth + columnGapPixels
targetProject = targetRibbon + finalRibbonWidth + columnGapPixels

For every output line, PadToTarget appends ordinary spaces and measures the entire growing prefix. It keeps the candidate closest to the target pixel width, instead of assuming that one character always equals a fixed width. Up to 1,024 padding attempts are allowed for a target.

The formatter then appends the Ribbon and Project values. This is the core trick: all rows use shared pixel targets even though a proportional font renders characters at different widths.

The generated text is a plain multi-line string, not an actual table widget. The TaskDialog expander receives it as its expanded information.

5.6 Phase E — diagnostics

The formatter records the selected mode, gap, budget, measured original width and fit state; any computed Ribbon/Project column budgets; individual truncation decisions (including original and shortened values); target column positions; approximate per-row alignment errors; and the longest measured line compared with the requested limit.

If the measured output still exceeds the limit, it emits a warning. The diagnostic explicitly distinguishes estimates made by TextRenderer from the real text positions used by Windows TaskDialog's DirectUI renderer.

6. MeasuredTextTruncationMode explained

Enum valueWhen the table fitsWhen the table overflowsTypical use
NoneAll values unchangedNo shortening; Windows may wrap lines and destroy column alignmentDebugging or preserving full text at the expense of layout
TruncateEndAll values unchangedShorten overflowing cells as Beginning…Values with distinctive beginnings
SmartAll values unchangedCompare Ribbon and Project values within each row: when a substantial common prefix exists, use …Ending; otherwise use Beginning…Paths, generated names, and similar values whose informative difference is at the end

The exact Smart decision in the source

HasMeaningfulCommonPrefix(a,b) performs an ordinal, case-insensitive comparison of Unicode text elements. It counts how many leading elements are equal. A common prefix is considered meaningful when both conditions hold:

commonPrefixElements >= 8
commonPrefixElements * 3 >= min(leftElementCount, rightElementCount)

That is, at least eight leading text elements must match, and the shared prefix must cover at least one-third of the shorter value. This heuristic works for the demonstrated long similar paths but is not a semantic path-comparison algorithm; it does not parse directories or treat filename extensions specially.

Examples

Input pairSmart choice if truncation is needed
C:\aaaaaaaa…aaaa12
C:\aaaaaaaa…aaaa34		Preserve suffixes, yielding values analogous to …aaaa12 and …aaaa34; exact retained length depends on width.
D:\Projects\Automation\Generated\Results
C:\Tmp\Output		Preserve beginnings if the shared-prefix threshold is not satisfied.

The choice to preserve endings is made for the pair of corresponding values, then applied to each cell that needs truncation. A value already within its budget is not shortened merely because the other value is long.

7. MeasuredSpacesExperiment — detailed design

This internal sealed class is an ordinary C# helper, not a Form and not a partial class. Its separation from TestForm is deliberate: double-clicking it in Visual Studio opens source code rather than launching a Form designer.

7.1 Fields and constructor

The Fields_GUI region holds references to the owning Form, a result Label, dataset and truncation ComboBox controls, gap and maximum-width NumericUpDown controls, and preview/diagnostic TextBox controls. The Fields_PresentedData region holds the generated text, diagnostic string and original values for later export.

Its constructor receives the controls from TestForm and retains those references. The constructor does not allocate a second WinForms form or set up a new message loop.

7.2 RebuildPreview()

  1. Reads the selected dataset index and maps it to comparison rows via GetMeasuredRows.
  2. Creates a temporary Graphics object using _owner.CreateGraphics(); it is disposed with using.
  3. Passes SystemFonts.MessageBoxFont, the selected gap and width, and the enum based on the truncation-selector index to MeasuredSpaceTableFormatter.Format.
  4. Saves Text, Diagnostics and FullValues from the returned result.
  5. Adds font name/point size and horizontal/vertical DPI to the displayed diagnostics, and updates the text boxes.
  6. On exception, clears the generated text and displays the exception details instead of opening a stale dialog.

The system message-box font is chosen as an approximation to the native TaskDialog DirectUI font. The font family, text metrics and DPI should be reviewed on the target system; an approximate match is not a pixel-perfect contract.

7.3 ShowDialog()

Calls RebuildPreview() first. If generated text is empty it stops. Otherwise it calls TaskDialogWrapper.QuestionYesNoCancel with moreDetails: _measuredGeneratedText and default button Yes. It writes the resulting DialogResult into the result label and appends it to diagnostics.

Despite the comparison headings, this is a test, not a production settings resolver: it demonstrates rendering and button return behavior, not modification of ACM Project or Ribbon data.

7.4 CopyTextAndDiagnostics()

Rebuilds the preview and puts a combined payload on the Windows clipboard: formatted text; full original, untruncated values; and diagnostics. This is important when displayed values have ellipses, because the clipboard still retains the information necessary to understand exactly what was compared.

7.5 GetMeasuredRows(int dataset)

Provides four built-in sample datasets:

Dataset indexPurpose
0 / defaultFour ordinary ACM settings: project name, output folder, create-at-least-a-script, safe cancel.
1Variable-width characters such as III, WWW, iiiii, MMMMMMMM; stresses proportional-font measurement.
2Long values and Unicode, including a Czech project name and directory; stresses overflow, Unicode and width assumptions.
3Long path pair with shared prefix but distinct endings, plus unrelated long names; stresses the Smart truncation heuristic.

Cases are local test data, not values loaded from an actual ACM Project.

8. Known limitations and engineering cautions

  • DirectUI versus TextRenderer: the measured font is an approximation. Native TaskDialog may have different font metrics or whitespace behavior.
  • Unknown native expander width: maxTableWidthPixels is user-configured and should be calibrated empirically. At different DPI, theme, locale or text size, the same budget can behave differently.
  • Whole-space granularity: padding cannot achieve fractional-space positioning; diagnostics report residual misalignment.
  • Wrapping is still possible: a row can exceed the estimated limit, especially if headers/labels cannot fit, or if native rendering differs from measured widths.
  • Loss of display detail: truncated dialog text is not the full source data; preserve complete values elsewhere for troubleshooting and accessibility.
  • Path semantics: Smart compares characters, not path components. Case-insensitive prefix matching does not imply the paths are logically equivalent.
  • Threading: Graphics, WinForms controls and modal dialogs must be used on the appropriate UI thread.
  • Localization: longer translated headers/settings may consume much of the width budget. Right-to-left text and other complex scripts need separate validation.

9. Plan for adopting the feature in another (possibly production) project

Recommended structure

Application / ViewModel └─ creates semantic differences (Setting, Left, Right) └─ ComparisonTextFormatter (shared formatting service) ├─ truncation policy and Unicode text-element logic ├─ text-width measurement abstraction └─ result { Text, Diagnostics, FullValues } └─ dialog adapter (WinForms TaskDialog / WPF host / other)
  1. Define a generic comparison model. Replace Ribbon/Project names in the formatter input with neutral Left/Right labels. Keep domain-specific settings generation in the application.
  2. Separate measurement from policy. Extract a small measurement interface or delegate (such as MeasureWidth(string)), so budget allocation, truncation and padding can be tested without WinForms.
  3. Preserve existing semantics. Keep None, TruncateEnd and Smart; make mode, gap, text-area limit and headers explicit parameters. Return full original values independently of display text.
  4. Keep native dialog invocation outside the formatter. Use TaskDialogWrapper or a small adapter to pass the formatted string into expanded information. Do not duplicate dialog result handling inside the formatting utility.
  5. Define fit expectations. Calibrate maximum usable width from representative target machines. Add tests for impossible budgets and situations where label and header widths dominate.
  6. Add automated tests. Assert no truncation if the complete table fits; ellipsis only when needed; suffix retention with meaningful common prefix; original-values preservation; Unicode-safe clipping; deterministic width budgets with a fake measurer; and useful diagnostics.
  7. Run UI verification. Confirm output on Windows at 100%, 125%, 150% DPI, on different fonts/themes, and for long localized paths. Track whether any line wraps in the real TaskDialog.
  8. Move into production only after visual verification. Keep this test harness as a regression/demo project.

10. Using the idea from WPF

A WPF application can adopt the same comparison strategy. There are two distinct objectives: (A) continue showing the native Windows TaskDialog with measured-space text, or (B) display a WPF-native comparison interface. These should not be confused.

Option A — WPF application calling native TaskDialog

Prefer this when preserving the Windows TaskDialog appearance is a requirement. Keep the TaskDialog adapter separate from WPF-specific code. If using the WinForms TaskDialogWrapper, the WPF project must reference the necessary Windows Forms assemblies. Supply the WPF owner window handle through WindowInteropHelper and, where required by the wrapper, a lightweight IWin32Window adapter. Do not assume a WPF Window can be passed as a WinForms IWin32Window directly.

For closest consistency with the test, the adapter can continue measuring using Windows Forms TextRenderer, with a temporary GDI Graphics context and an appropriate system font. This avoids having WPF-only text measurements drift from the native TaskDialog's font approximation, but it adds a Windows Forms dependency and still does not guarantee perfect DirectUI matching.

// Conceptual integration:
// 1. Build ComparisonRow values in WPF view model.
// 2. Format them using the shared measured-space formatter.
// 3. Obtain HWND with new WindowInteropHelper(wpfWindow).Handle.
// 4. Adapt HWND to IWin32Window if using TaskDialogWrapper.
// 5. Call QuestionYesNoCancel(..., moreDetails: result.Text).

Only the application/dialog-adapter layer needs to understand WPF window ownership. The truncation and alignment policy should remain reusable.

Option B — WPF-native comparison

If exact columns are more important than preserving the native TaskDialog, use a WPF Grid, DataGrid or equivalent with three real columns. WPF already provides text trimming, wrapping, tooltips and column sizing. In that case, measured-space padding is usually unnecessary, although the Smart truncation policy can still help decide which portion of a long paired value to show.

WPF text measurement

WPF offers FormattedText, constructed with a Typeface, size, culture, flow direction and pixelsPerDip. WidthIncludingTrailingWhitespace is especially relevant when measuring padded strings because Width excludes trailing whitespace. WPF measures in device-independent pixels (DIPs); if a shared formatter uses physical-pixel budgets, convert units consistently with the rendering scale. A WPF FormattedText measurement is not automatically identical to WinForms TextRenderer or TaskDialog DirectUI rendering.

// Example of WPF-side text measurement (schematic):
double MeasureWpfText(string value, Typeface typeface,
                      double fontSizeDip, double pixelsPerDip)
{
    var ft = new System.Windows.Media.FormattedText(
        value,
        System.Globalization.CultureInfo.CurrentUICulture,
        System.Windows.FlowDirection.LeftToRight,
        typeface,
        fontSizeDip,
        System.Windows.Media.Brushes.Black,
        pixelsPerDip);
    return ft.WidthIncludingTrailingWhitespace; // DIPs
}

11. Verification and acceptance checklist

  • Original ACM sample: three columns appear aligned and text is not truncated when the table fits.
  • Variable-width character sample: same measured target positions despite i/W/M width differences.
  • Long Unicode sample: no unexpected wrapping under selected maximum width; clip only where required.
  • Shared long prefix: Smart mode retains distinguishing suffixes such as …12 versus …34.
  • Unrelated long values: Smart mode keeps beginnings and appends ellipsis.
  • None mode: long strings remain untouched, with a warning if they might wrap.
  • Full source values can be copied even if the dialog shows truncated strings.
  • Repeat with another width, with the gap adjusted, and on 125%/150% display scaling.
  • Check Yes, No, Cancel results and all pre-existing TaskDialog demonstration buttons.
  • Verify the actual project builds in both relevant target framework configurations; the documentation itself does not establish successful compilation.

Suggested next development tasks

First establish an explicit maximum-width policy and test it under Windows DPI variations. Next extract generic row data and a text-measurement abstraction. Then create a small reusable library API, leaving actual modal dialog display with the caller or a dialog adapter. Finally exercise the integration from a WinForms and, if needed, WPF sample before using it for production ACM settings comparisons.
