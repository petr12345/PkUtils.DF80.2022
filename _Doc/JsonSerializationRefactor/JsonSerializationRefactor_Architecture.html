PkNetUtils JSON serialization refactor

Implemented architecture · class relationships · data contracts · compatibility

The goal is to replace obsolete binary object serialization with explicit JSON contracts for persistent settings, shared-memory transfer, cloning and affected samples. Existing public API shapes are retained where practical; implicit serialization of arbitrary CLR graphs is replaced by documented, supported contracts.

1. Application storage

ApplicationStorage<T> derives directly from Dictionary<string, T> and persists a JSON dictionary in isolated storage. ApplicationObjStorage specializes it for object-valued settings using an explicit runtime-type registry and converter. No legacy binary-storage class hierarchy is retained.

Save() serializes the complete dictionary to UTF-8 bytes before opening the settings file, preventing serializer failures from truncating a previously valid store. SafeLoadData() records supported load failures in LastSafeLoadResult; it returns void. LastLoadFoundAnyStorage records whether the expected JSON file was found.

The default object registry supports Int32, Point, Size and Rectangle. Register additional JSON-compatible runtime types before constructing an instance that loads them.

ApplicationObjStorage.RegisterType<MySettings>("MySettings-v1");
ApplicationObjStorage storage = new(true);
storage["settings"] = new MySettings();
storage.Save();

MySettings is an application-defined example type, not a library class. Object-storage registrations are process-wide; serializer options are held per storage instance and can be customized through ConfigureSerializerOptions.

2. Shared JSON helpers

JsonObjectTypeRegistry maintains mappings in both directions and synchronizes registration and lookup. Repeating the same registration is allowed; reassigning a type or discriminator is rejected. System.Object, abstract/interface types, open generic types, pointer/by-ref types and void are rejected as payload registrations.

ApplicationObjStorageJsonConverter delegates to RegisteredObjectJsonConverter. It does not inherit from that converter. Both converters inherit from the framework JsonConverter<object>. The registry reference is shared rather than exclusively owned.

{
  "window-width": { "$type": "Int32", "$value": 1024 },
  "window-location": { "$type": "Point", "$value": { "X": 40, "Y": 60 } }
}

Each non-null object value carries a stable $type discriminator and a typed $value. Null storage values remain JSON null. The reader rejects unknown discriminators instead of resolving arbitrary assembly-qualified names. Root type registration does not automatically configure every nested polymorphic property.

3. Shared-memory object transfer

Segment adds a versioned JSON envelope above the unchanged native mapping, attachment, capacity and mutex behavior. It holds a separate, initially empty JsonObjectTypeRegistry, plus a static serializer configuration using the reusable registered-object converter.

{
  "$format": "PK.PkUtils.SharedMemory.Json",
  "$version": 1,
  "$data": {
    "$type": "PersonData-v1",
    "$value": { "Age": 37, "Name": "Liška podšitá", "DummyArray": [0, 1, 2] }
  }
}

This is a shortened illustrative payload based on the test-fixture PersonData contract; the separate client/server sample names its array property Arr. Actual array contents are serialized in full.

Segment.RegisterType<PersonData>("PersonData-v1");

Both writer and reader processes must perform this registration before transfer. They can use compatible CLR contracts in different assemblies, but must agree on the discriminator, JSON structure, format and version. ApplicationObjStorage registration does not register a Segment payload.

ObjectToStream writes the envelope; ObjectFromStream reads it and validates the format/version. Both are protected static helpers. GetData copies the native payload and delegates to the reader helper; SetData checks capacity before copying a complete serialized payload. JSON and unsupported-contract errors are wrapped in SharedMemoryException with the original exception retained.

4. Cloning and API compatibility

CloneHelperJson serializes and deserializes using the original object’s runtime type. Default options include public fields and enable ReferenceHandler.Preserve for supported mutable graphs. Cycles and repeated references are tested. Nested polymorphism requires explicit JSON attributes or caller-configured options.

MakeCloneableBinary<T> implements IDeepCloneable<T> and calls CloneHelperBinary. It does not inherit from CloneHelperJson. Both helper types are static classes. ToByteArray returns UTF-8 JSON and returns null for a null source; its output is not compatible with earlier formatter bytes.

Private-field state and formatter callbacks are not automatically copied. Immutable types need a JSON-compatible constructor or converter. The modified BSID contract and immutable cloning fixtures explicitly select their JSON constructors.

5. Tagging-editor DTOs

TaggingSchemaJson<TFIELDID> persists only logical text and ordered field positions/identifiers. Its nested SchemaData and FieldData classes form the JSON contract. The receiving control supplies the substitution map; the map is not persisted as arbitrary CLR objects.

{
  "Format": "PK.TaggingSchema.Json",
  "Version": 1,
  "Text": "abc",
  "Fields": [ { "Identifier": "project-title", "Position": 2 } ]
}

The illustrated string identifier applies to a class-based FieldTypeId schema. Enum-based schemas serialize the enum directly using default numeric enum handling. The converter’s fixed allow-list includes project-title, document-author, document-title, copyright, year, month, day-of-week, dog, resistance, diameter and project-name.

The reader rejects unsupported/incomplete format versions and invalid field positions. LogInfo<TFIELDID> equality compares field identity and position instead of comparing serialized bytes. File-dialog ordering is retained while the binary option becomes JSON.

7. Compatibility boundaries

No automatic legacy fallback: old application .dtt files and binary tagging files are not automatically read or migrated. Old binary shared-memory processes are not wire-compatible with the new JSON protocol; upgrade participants together.

JSON contracts must preserve required state explicitly. Stable discriminators separate protocol identity from CLR assembly identity, but do not automatically make incompatible data schemas compatible. Isolated storage is not encryption or tamper protection.

Project formatter settings/package references and CLS-compliance declarations were removed. Unrelated XML/DataContract serializers, obsolete compatibility declarations and native byte/struct operations were retained where no modification was needed.
